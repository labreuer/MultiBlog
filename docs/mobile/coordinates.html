Two Coordinate Spaces

Every floating popover in the app was written in the coordinate space you measure in, then handed to a CSS property that reads a different one. On desktop the two spaces coincide, so the bug stayed invisible for as long as the code existed. An iPad with its keyboard up pulls them 262 pixels apart.

Measured on iPadOS 18.6 · Safari 605.1.15 · landscape 1194×727 Instrument scripts/remote-console.ts Date 2026-08-30

The scheme, as it stood

A selection popover cannot be position: absolute: its nearest scrolling ancestor clips it — on /side-by-side that is the column's own .scroller, and CSS cannot leave one axis visible while clipping the other. So every popover here is position: fixed, which escapes the clip and, in exchange, has no containing block to be laid out against. The clamping has to be done by hand.

That hand-clamping was three stages. Measure the anchor with coordsAtPos or getBoundingClientRect; run placePopover to slide it horizontally and flip it vertically inside a bounds rectangle; write the result into the element's inline top / left. The bounds rectangle came from window.innerWidth and window.innerHeight.

Where it breaks

Two facts about iOS, each harmless alone. First: getBoundingClientRect reports position relative to the visual viewport — the part of the page the reader can actually see. Second: while the software keyboard is up, Safari stops anchoring position: fixed to the viewport and anchors it to the document instead.

So the measurement returns a number in screen space, and the CSS property interprets that same number in document space. The two spaces are offset by scrollY. On a desktop browser scrollY never enters into it, because fixed is viewport-anchored there and the conversion is the identity — which is exactly why nothing ever went wrong.

The third failure: the keyboard fires no window event

Repositioning was subscribed to window's scroll and resize. Raising the keyboard fires neither. On the recorded trace, visualViewport.height went 727 → 299 while window.innerHeight stayed at 727 and no window event fired at all; the first scroll arrived 2.5 seconds later, when Safari got round to scrolling the caret into view. A popover listening only to window sits still through the exact moment the viewport shrinks under it. onViewportChange now subscribes to both.

The trap in the obvious fix

The conversion looks like it should be top - window.scrollY. It must not be: on a desktop browser fixed is correctly viewport-anchored while scrollY is non-zero on any scrolled page, so subtracting it unconditionally would push every popover in the app off-screen. The obvious guard is a user-agent test, and that fails here too — an iPad in its default desktop mode reports Macintosh; Intel Mac OS X 10_15_7. The device exhibiting the bug is precisely the one UA sniffing calls a Mac.

So fixedAnchorShift() measures instead of deducing: a zero-size fixed probe is parked in the document, and its own getBoundingClientRect().top is the discrepancy. It reads 0 wherever there is nothing to correct, and -scrollY where there is. No allowlist, and it stays right if Safari changes its mind.

What changed on desktop

The conversion stage is a no-op on desktop — the probe reads zero, so not one pixel moves because of it. The clamp is the part that genuinely changed: popoverBoundsFor used to read window.innerWidth and now reads visualViewport.width. Those differ by exactly one thing, the classic scrollbar.

window.innerWidth includes the scrollbar's width; visualViewport.width excludes it, and comes out identical to document.documentElement.clientWidth. So a popover clamped to the old bounds could be pushed to a right edge that sits underneath the scrollbar; clamped to the new bounds it stops clear of it.

That is the more correct behaviour — a scrollbar is not space a popover should sit under — but it is a change to every popover in the app, not only the ones an iPad ever sees.

What @floating-ui/dom already does

The popovers moved to @floating-ui/dom after this was written (computePosition + autoUpdate per call site), and the library turns out to own both halves of the problem on its own surfaces — so most of what is described above is no longer ours to do:

  • getViewportRect Reads visualViewport.width/height for the default 'viewport' boundary, so flip() and shift() already clamp to the visual viewport. It even branches on WebKit explicitly: layoutRelativeClientCoords = !isWebKit() || strategy === 'fixed'.
  • autoUpdate Binds scroll and resize to every entry getOverflowAncestors returns — and that list includes win.visualViewport. That is exactly what onViewportChange exists to do, so a floating-ui surface needs none of it.

The rule that survives

Never wrap a computePosition result in fixedPlacementStyle. Its x/y come back already in the floating element's own positioning space; converting again applies the shift twice. The helper is for coordinates we compute and write — the marker, and the header panels.
