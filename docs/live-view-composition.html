The live-viewing surfaces, before and after the split

Two routes render live, collaboratively-updating doc content: the reading view at /doc/[slug], where selecting text offers to annotate it, and the side-by-side column at /side-by-side/[left]/[right], where the same gesture creates a doc link. Both need the same Hocuspocus tap and the same selection handling. The question each diagram answers is where that overlap was drawn.

What the colours are actually showing

In the first diagram every rose line and every teal line passes through the same amber box. That is not a drawing artefact — it is the arrangement. The reading view mounted a component carrying twelve props of doc-link machinery it never used, and the two views shared one pending field, which is precisely how a doc-link change mispositioned annotations on a page it never touched.

In the second, rose and teal never meet. They converge only on slate — the live tap and the selection gesture, the parts that are identical rather than merely similar. That is the same rule the write column already followed: CollabEditorBody.tsx is reused by DocColumn unchanged, because the write surface wanted the same behaviour rather than a variation of it.

The cost is visible too. What was one file readable top to bottom is now a contract across three, and the shared editorRef is a piece of load-bearing structure a reader has to understand. That is the trade: more indirection, in exchange for two surfaces that can no longer break each other.
