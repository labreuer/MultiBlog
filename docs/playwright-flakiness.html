Run overnight 2026-08-22 → 23 on the Windows desktop (i7-8700K, 6c/12t) · full suite (148 tests) × 10 rounds at workers 1, 2, and 3, interleaved, against one warm dev stack with both servers' output captured — the view Playwright normally can't see.

The suite is not one flaky thing — it is five separate diseases, and every observed failure traces to exactly one of them. The worst is not load-related at all: a keystroke-timing race in one spec's Ctrl+A → ArrowLeft → type recipe wiped 20 of 30 runs at every worker count, including single-worker at idle. Beneath it sits the historical pattern the config comment describes: a confirmed upstream next dev manifest-corruption bug firing ~once per run, a dev-only next-auth invariant that turns a transient SSR miss into a 500, dev-server queueing that only bites at 3 workers, and three small test-design races. All five have concrete fixes; the top one is proven working (6/6 on the real test, 24/24 on the isolated repro). The dev stack is fragile in dev-only ways — but most of tonight's red was ours, not Next's.

CLASS 1 20 / 30 RUNS FIX PROVEN

The select-all wipe — a keystroke race, not a load problem

quote-anchoring.spec.ts:83 · failed 7× at w1, 6× at w2, 7× at w3 · reproduces ~50% solo on an idle server

The spec types Ctrl+A → ArrowLeft → "Yesterday, " to prepend text. At synthetic keystroke speed (~15 ms gaps), ProseMirror's ingestion of the native ArrowLeft collapse races the typing: the DOM selection collapses (instrumented and confirmed), but PM's state selection is still the full-document AllSelection when the first character arrives — so the character replaces the entire document, and the deletion syncs to the server as a legitimate edit. The editor ends up containing exactly "Yesterday, ".

What it is not, established by elimination: not the annotation widget's deferred setPendingAnnotation dispatch (no-opping capture entirely still wiped 7/12); not the late-arriving collab seed (the instrument shows the seed present and selected in most wiped iterations); not my log-piping setup (bare servers: 5/12). Inserting a 75 ms pause between the keys cuts it sharply but not to zero — the ingest window is usually, not always, that short. A human typing at >50 ms gaps essentially can't hit it, which is why the app is fine and only the suite bleeds.

Fix — proven

Replace the chord with the codebase's own documented programmatic idiom: build a collapsed DOM Range at the body's first text node, dispatch selectionchange, then type. 12/12 clean in isolation, and the real test passes 6/6 with the patch (it failed 67% of tonight's runs unpatched):

await page.evaluate(() => {
  const root = document.querySelector('[aria-label="Post body"]');
  const node = document.createTreeWalker(root, NodeFilter.SHOW_TEXT).nextNode();
  const range = document.createRange();
  range.setStart(node, 0);
  range.collapse(true);
  const sel = window.getSelection();
  sel.removeAllRanges();
  sel.addRange(range);
  document.dispatchEvent(new Event("selectionchange"));
});
await page.keyboard.type(prefix);

Worth promoting to a fixtures helper (collapseToBodyStart(page)) beside selectTextInBody, and auditing any other spec that types immediately over a fresh selection.

CLASS 2 1 / 30 DIRECT LATENT EVERYWHERE

"🟢 Live" means connected, not synced

quote-anchoring.spec.ts:117 · "fox " not found in an empty editor, at workers=1

DocEditor's badge is set from Hocuspocus's onStatus — which fires at websocket open (provider source, line 219), before authentication, onLoadDocument's DB read, and the syncStep2 that actually delivers content (line 502). So waitForDocCollabReady, the gate every editing spec trusts, proves only that a socket opened. The gap is milliseconds when idle and hundreds under load; one run caught deleteTextInBody walking a still-empty editor after the gate passed. The warm-up trace shows the same thing from the other side: "Live" resolved ~330 ms before the seed arrived.

Fix

Expose synced-ness and gate on it. The reading views already model this — doc.spec.ts waits on a live-doc-synced test id. Either make the badge itself require connected && synced (arguably truer UX: "Live" currently shows before the doc's content is in), or add a data-synced attribute to the status line and have waitForDocCollabReady wait for that. One change fixes the class for every editing spec at once.

CLASS 3 17 TEARS · 1 KILL UPSTREAM, OPEN

next dev corrupts its prerender manifest under concurrency

vercel/next.js #96664 (fix PR unmerged) · fired at every worker count · killed landing.spec in r2-w3

loadStaticPaths does a read-modify-write of .next/dev/prerender-manifest.json with no lock and no atomic rename — verified in the installed 16.2.11. One route has generateStaticParams — /[slug] — and its revalidate = 60 makes dev re-run it every minute, so this fires all night with zero recompiles — 17 tears in this session. The catch explains both outcomes: a request holding a stale cached result absorbs the tear with just a log line; a cold-cache request 500s — and the parse failure evicts the cache entry, so the next request runs cold too (bursts of 2–3 tears seconds apart, observed twice).

Correction, 2026-08-26. That sentence originally read “Three routes have generateStaticParams (/[slug], /doc/[slug], /pdf/[slug])”. It was wrong the day it was written, not merely overtaken: git log -S 'export async function generateStaticParams' returns nothing at all for the other two files — the export has never existed in either. Both name the identifier only inside a comment forbidding it (“no generateStaticParams, and none should be added”; PLAN.md §12f — a statically-eligible route that also calls a dynamic API throws DYNAMIC_SERVER_USAGE at build). A grep counts mentions, and a comment explaining why something is absent reads exactly like the thing being present.

What survives, and what does not. The 17 tears are an observation and stand unchanged; the upstream mechanism is verified present in the installed 16.2.11 either way. What the miscount inflated is the explanation of the rate — one route re-running every 60 s, not three. Note also what was never measured: whether /authors/[slug] (dynamic segment, revalidate = 60, no generateStaticParams) or the non-dynamic revalidating routes (/, /rss.xml) reach loadStaticPaths at all. So the true feed rate is one route plus an unmeasured remainder — which is the honest shape of it, and a reason the mitigations below never depended on the count.

The collateral reaches routes that don't even use static params: the one landing.spec failure was GET / 500 in 3.2s (next.js: 3.0s, application-code: 217ms), three seconds after a tear — invisible to the spec because it used plain goto, so it read as "contributor missing". Two reattributions follow: the config comment's "server actions arriving with truncated bodies — Unexpected end of JSON input" is this bug's error string (Next failing to parse its own manifest; the real body-truncation bug, #85810, is fixed in 16.2.11 and required a middleware this repo doesn't have). And "all pass under --workers=1" is no longer a reliable tell — the tear is concurrency-triggered, not worker-triggered; dev prefetches alone provide the concurrency.

Mitigations (no upstream fix in any released version)
  • Run the suite against the prod build — web-prod already exists; Next's own Playwright guide recommends exactly this. Kills classes 3 and 4 outright and removes compile-latency noise. Cost: a build per session, and :3001 wiring.
  • Staying on dev: use gotoOk for every public-page navigation (13 plain gotos today) so a tear at least names itself instead of masquerading as a missing element.
  • Cheap tripwire: JSON.parse the manifest in check-ports (devManifestIsTorn, scripts/dev-servers.ts) — the sticky variant of this bug 500s every route until restart and is otherwise indistinguishable from "the suite broke".

CLASS 5 12 OF 16 W3 FAILURES 3 SMALL FIXES

The workers=3 scatter — queueing, plus three real test bugs it exposes

doc.spec:325 ×4 · admin-table:122 ×3 · pdf-annotations:332 ×2 · doc:387, doc:578, doc:169, landing ×1 each

At 3 workers, ~11 requests per run take ≥1 s and the tail reaches into 10–30 s budgets. Most of the scatter is plain latency (annotation-composer opens, a sign-in redirect). But three of the recurring ones are deterministic bugs that load merely exposes:

  • doc.spec.ts:325 — getByText(...).first() on an annotation body that exists twice in the DOM (§13p: hidden SSR copy + live copy). .first() pins whichever is DOM-first; mount timing decides visibility. The README already documents this trap for post bodies and provides visibleText() — this call site needs the same .filter({ visible: true }), and the other dual-copy .first()s deserve an audit.
  • admin-table.spec.ts:122 — trace-verified: the final "Set role → AUTHOR" selectOption produced no POST at all. The spec re-checks rows right after a Restore whose only settle-signal is the row border — which turns SAVED from client state before the action's RSC refresh lands. The refresh then replaces the table, resets the selection, and the bulk apply silently no-ops against zero rows. Every server action in all three failure windows returned 200 in <700 ms — the server was never the problem. Fix: assert server truth after Restore (the row's Delete button is back) before re-selecting; or make selection survive the refresh in the component.
  • doc.spec.ts:169 — one teardown failure: Refusing to delete doc … non-throwaway (or missing) author, the db.ts containment guard tripping on a fixture-teardown ordering race under parallelism.
Verdict on workers

The committed default of 2 remains right for this machine. 3 buys the same ~200 s wall clock as 2 (fixed costs dominate a 148-test suite; the ~50 s in the README predates its growth) while tripling the ≥1 s stragglers — all cost, no speed.

  • tighten.spec — a keystroke inside a deferred focus(). The test clicks a toolbar button and presses Ctrl+Z; on this box the two toHaveCount()s between them settle in ~30 ms. CLASS 6 6 OF 8 POSTS STALLED FIX PROVEN

A refresh transition that never commits, behind an ssr: false boundary

pdf-annotations.spec.ts · prod build, one worker · 1–4 failures per run before · 23/23 ×3 and a full suite green ×2 after

Post an annotation on /pdf/[slug] and the panel goes on reading No annotations yet. The composer's router.refresh() is a React transition, and the whole viewer sits behind next/dynamic({ ssr: false }) — which is a Suspense boundary. During a transition React deliberately keeps showing the old UI rather than dropping to a fallback, so a render that never commits is completely silent: no error, no spinner, no console line, no failed request, not even a flash. From the outside it is indistinguishable from a spec that looked too early — and that reading is always available and always cheaper to believe.

The data was on the client every time. The _rsc GET returned 200 carrying the annotation, and the payload was byte-identical between a passing and a failing run: len=7327 rows=20 refs=18 MISSING=[], with correct quads, quote.exact and root.body all present. Nothing was lost, refused, truncated or deprioritised on the wire — which killed every request-side explanation at once, the four classes above included.

A probe over 8 iterations then measured the client directly, walking up from the tab panel's __reactFiber$ and reading memoizedProps.entries.length off every ancestor fiber that carries one (three do, hence a triple):

The split in those middle two rows is worth stating plainly rather than smoothing into a slogan. In half the stalls the transition had genuinely not committed; in the other half it had, without the card being on screen when the spec looked. So “the transition never commits” is the majority case and not the whole of it. What both halves share is the part that matters: the commit is unmoored from the post, landing whenever React next has some reason to do work — which is exactly why an unrelated click is a reliable cure, and why no amount of waiting fixes it honestly. A longer timeout would only be betting on some other event happening to arrive.

One further control: git stash, and the clean tree flakes identically — a different subset of iterations each run. Nothing about the branch under development was implicated.

Fix — proven

Stop asking the router to deliver the list, and fetch it. PdfAnnotationSurface keeps the server's entries prop as its source of truth and overlays a locally fetched copy: a server action (loadPdfAnnotationEntries, permission-gated in its own right, since a client can send whatever id it likes) returns the same shape the page builds, and the composer, every card's Reply and every card's Delete call one context-provided reload(). Because the fetch is ours, its setState is not a transition and commits at normal priority. router.refresh() still runs underneath — it is what reconciles the rest of the page — and the overlay stands down the moment a new entries identity arrives, so it never hardens into a second source of truth.

The stand-down is keyed on prop identity (refetched?.base === entries ? refetched.list : entries) rather than an effect that nulls the overlay when the prop changes. The effect version is the obvious one and it is wrong twice over: it trips “Calling setState synchronously within an effect can trigger cascading renders”, and it spends a render discovering what an identity comparison already knows.

Result: pdf-annotations.spec.ts 23/23 three times running, against a baseline of 1–4 failures per run; and the full suite green twice before the fix was committed, plus 169/169 again after merging it onto a main that had moved.

Where else this can bite

The precondition is narrow and worth carrying as a shape: a client island behind ssr: false whose content arrives only through router.refresh(). /doc/[slug] is not exposed — its annotations render straight out of the server tree with no such boundary, which is why the shared reload context defaults to a no-op there instead of being wired in everywhere for symmetry. Any future ssr: false island rendering a server-owned list needs either the same treatment or an explicit argument for why it does not.

Benign noise, catalogued

Seen in the captured logs, correlated against outcomes, and harmless — worth recognizing so they don't get re-investigated: the [doc-cache] ForeignKeyConstraintViolation (store-debounce racing fixture deletion — the documented logged-and-discarded case), Doc not found after teardown, Error: aborted when a context closes mid-request, permission-denial logs from doc-visibility's deliberate denial tests, and Author list changed — please retry optimistic-concurrency retries.

Added 2026-08-24, from the prod worker matrix: Invalid prisma.annotation.create() — Foreign key constraint violated on annotation_file_id_fkey, once in six full runs. Same family as the [doc-cache] entry above — a fixture hard-deleting a parent row while a request that references it is still in flight — but it deserves its own line because it is louder: it surfaces as an unhandled ✖ Error with a stack and a digest rather than a logged-and-discarded warning, so it reads like a real fault and will stop whoever finds it.

Three facts make it safe to leave. It cannot happen in production: it requires a hard storedFile.delete, and the app only ever soft-deletes a file (deletedAt, src/app/actions/files.ts) — the hard delete exists solely in e2e/db-worker.ts's deleteTestFile and scripts/test-file.ts. It is not an unawaited click: both UI call sites that post a file annotation already wait for the composer to reset before returning (pdf-annotations.spec.ts, pdf-presence.spec.ts), the second having been added when this class was fixed the first time. And it is not fully fixable from the fixture side: the create is a server action, so closing the page does not cancel work Node has already begun — no teardown ordering prevents an in-flight action from landing after its parent row is gone.

What would change that: if a permanent-delete for files is ever added to the app, this stops being fixture-only and the annotation path needs to fail gracefully on a missing file rather than throwing P2003.
