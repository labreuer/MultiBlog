The suite is not one flaky thing — it is five separate diseases, and every observed failure traces to exactly one of them. The worst is not load-related at all: a keystroke-timing race in one spec's Ctrl+A → ArrowLeft → type recipe wiped 20 of 30 runs at every worker count, including single-worker at idle. CLASS 1 20 / 30 RUNS FIX PROVEN

The select-all wipe — a keystroke race, not a load problem

quote-anchoring.spec.ts:83 · failed 7× at w1, 6× at w2, 7× at w3 · reproduces ~50% solo on an idle server

The spec types Ctrl+A → ArrowLeft → "Yesterday, " to prepend text. At synthetic keystroke speed (~15 ms gaps), ProseMirror's ingestion of the native ArrowLeft collapse races the typing: the DOM selection collapses (instrumented and confirmed), but PM's state selection is still the full-document AllSelection when the first character arrives — so the character replaces the entire document, and the deletion syncs to the server as a legitimate edit. The editor ends up containing exactly "Yesterday, ".

What it is not, established by elimination: not the annotation widget's deferred setPendingAnnotation dispatch (no-opping capture entirely still wiped 7/12); not the late-arriving collab seed (the instrument shows the seed present and selected in most wiped iterations); not my log-piping setup (bare servers: 5/12). Inserting a 75 ms pause between the keys cuts it sharply but not to zero — the ingest window is usually, not always, that short. A human typing at >50 ms gaps essentially can't hit it, which is why the app is fine and only the suite bleeds.

Fix — proven

Replace the chord with the codebase's own documented programmatic idiom: build a collapsed DOM Range at the body's first text node, dispatch selectionchange, then type. 12/12 clean in isolation, and the real test passes 6/6 with the patch (it failed 67% of tonight's runs unpatched):

await page.evaluate(() => {
  const root = document.querySelector('[aria-label="Post body"]');
  const node = document.createTreeWalker(root, NodeFilter.SHOW_TEXT).nextNode();
  const range = document.createRange();
  range.setStart(node, 0);
  range.collapse(true);
  const sel = window.getSelection();
  sel.removeAllRanges();
  sel.addRange(range);
  document.dispatchEvent(new Event("selectionchange"));
});
await page.keyboard.type(prefix);

Worth promoting to a fixtures helper (collapseToBodyStart(page)) beside selectTextInBody, and auditing any other spec that types immediately over a fresh selection.

CLASS 2 1 / 30 DIRECT LATENT EVERYWHERE

"🟢 Live" means connected, not synced

quote-anchoring.spec.ts:117 · "fox " not found in an empty editor, at workers=1

DocEditor's badge is set from Hocuspocus's onStatus — which fires at websocket open (provider source, line 219), before authentication, onLoadDocument's DB read, and the syncStep2 that actually delivers content (line 502). So waitForDocCollabReady, the gate every editing spec trusts, proves only that a socket opened. The gap is milliseconds when idle and hundreds under load; one run caught deleteTextInBody walking a still-empty editor after the gate passed. The warm-up trace shows the same thing from the other side: "Live" resolved ~330 ms before the seed arrived.

Fix

Expose synced-ness and gate on it. The reading views already model this — doc.spec.ts waits on a live-doc-synced test id. Either make the badge itself require connected && synced (arguably truer UX: "Live" currently shows before the doc's content is in), or add a data-synced attribute to the status line and have waitForDocCollabReady wait for that. One change fixes the class for every editing spec at once.

CLASS 3 17 TEARS · 1 KILL UPSTREAM, OPEN

next dev corrupts its prerender manifest under concurrency

vercel/next.js #96664 (fix PR unmerged) · fired at every worker count · killed landing.spec in r2-w3

loadStaticPaths does a read-modify-write of .next/dev/prerender-manifest.json with no lock and no atomic rename — verified in the installed 16.2.11. Three routes have generateStaticParams (/[slug], /doc/[slug], /pdf/[slug]), and revalidate = 60 makes dev re-run it every minute, so this fires all night with zero recompiles — 17 tears in this session. The catch explains both outcomes: a request holding a stale cached result absorbs the tear with just a log line; a cold-cache request 500s — and the parse failure evicts the cache entry, so the next request runs cold too (bursts of 2–3 tears seconds apart, observed twice).

The collateral reaches routes that don't even use static params: the one landing.spec failure was GET / 500 in 3.2s (next.js: 3.0s, application-code: 217ms), three seconds after a tear — invisible to the spec because it used plain goto, so it read as "contributor missing". Two reattributions follow: the config comment's "server actions arriving with truncated bodies — Unexpected end of JSON input" is this bug's error string (Next failing to parse its own manifest; the real body-truncation bug, #85810, is fixed in 16.2.11 and required a middleware this repo doesn't have). And "all pass under --workers=1" is no longer a reliable tell — the tear is concurrency-triggered, not worker-triggered; dev prefetches alone provide the concurrency.

Mitigations (no upstream fix in any released version)
  • Run the suite against the prod build — web-prod already exists; Next's own Playwright guide recommends exactly this. Kills classes 3 and 4 outright and removes compile-latency noise. Cost: a build per session, and :3001 wiring.
  • Staying on dev: use gotoOk for every public-page navigation (13 plain gotos today) so a tear at least names itself instead of masquerading as a missing element.
  • Cheap tripwire: JSON.parse the manifest in check-ports.ps1 — the sticky variant of this bug 500s every route until restart and is otherwise indistinguishable from "the suite broke".
CLASS 4 0 / 30 HERE · KILLED THE 11:09 RUN

The dev-only useSession 500

next-auth invariant, dev builds only · needs a rebuild window · absent from steady-state runs by design

Your last pre-session run (yesterday 11:09) failed publish.spec with a 500 whose body carries the full stack: [next-auth]: useSession must be wrapped in a <SessionProvider /> thrown from CommentForm during SSR of /[slug] — while the root layout demonstrably wraps everything. The throw is env-gated (process.env.NODE_ENV !== "production", verified in the installed copy): in production the same context miss renders as "signed out"; in dev it's a 500. The trigger profile matches Turbopack serving a mixed SSR module graph during rebuild windows (dev re-reads manifests per request while the bundler rewrites them — #97594). My 30 runs had no source edits, hence no rebuilds, hence zero occurrences — your normal edit-and-rerun workflow has them constantly. No exact upstream issue exists; the recovered stack would make a strong report.

Fix

Nothing to change in the app — the layout is correct. Testing against the prod build removes the class; otherwise it remains a background rate tied to how often the dev server is compiling while the suite runs.

CLASS 5 12 OF 16 W3 FAILURES 3 SMALL FIXES

The workers=3 scatter — queueing, plus three real test bugs it exposes

doc.spec:325 ×4 · admin-table:122 ×3 · pdf-annotations:332 ×2 · doc:387, doc:578, doc:169, landing ×1 each

At 3 workers, ~11 requests per run take ≥1 s and the tail reaches into 10–30 s budgets. Most of the scatter is plain latency (annotation-composer opens, a sign-in redirect). But three of the recurring ones are deterministic bugs that load merely exposes:

  • doc.spec.ts:325 — getByText(...).first() on an annotation body that exists twice in the DOM (§13p: hidden SSR copy + live copy). .first() pins whichever is DOM-first; mount timing decides visibility. The README already documents this trap for post bodies and provides visibleText() — this call site needs the same .filter({ visible: true }), and the other dual-copy .first()s deserve an audit.
  • admin-table.spec.ts:122 — trace-verified: the final "Set role → AUTHOR" selectOption produced no POST at all. The spec re-checks rows right after a Restore whose only settle-signal is the row border — which turns SAVED from client state before the action's RSC refresh lands. The refresh then replaces the table, resets the selection, and the bulk apply silently no-ops against zero rows. Every server action in all three failure windows returned 200 in <700 ms — the server was never the problem. Fix: assert server truth after Restore (the row's Delete button is back) before re-selecting; or make selection survive the refresh in the component.
  • doc.spec.ts:169 — one teardown failure: Refusing to delete doc … non-throwaway (or missing) author, the db.ts containment guard tripping on a fixture-teardown ordering race under parallelism.
Verdict on workers

The committed default of 2 remains right for this machine. 3 buys the same ~200 s wall clock as 2 (fixed costs dominate a 148-test suite; the ~50 s in the README predates its growth) while tripling the ≥1 s stragglers — all cost, no speed.

Benign noise, catalogued

Seen in the captured logs, correlated against outcomes, and harmless — worth recognizing so they don't get re-investigated: the [doc-cache] ForeignKeyConstraintViolation (store-debounce racing fixture deletion — the documented logged-and-discarded case), Doc not found after teardown, Error: aborted when a context closes mid-request, permission-denial logs from doc-visibility's deliberate denial tests, and Author list changed — please retry optimistic-concurrency retries.
