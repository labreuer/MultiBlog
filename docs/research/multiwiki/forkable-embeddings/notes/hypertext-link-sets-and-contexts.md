# Hypertext-research precedents for "embeddings": link sets, contexts/layers, emergent structure, and multiple interpretations

Research done 2026-09-22. Scope: hypertext systems and papers (1980–2002) that anticipated any of the four embedding features. Shorthand used throughout:

- **F1**: whole entities *or parts (passages)* can be assigned to one or more embeddings.
- **F2**: *relationships between entities* can be assigned to an embedding.
- **F3**: embeddings can *fork* from one another (and, by implication, be compared and merged).
- **F4**: an assignment records the entity's *revision*; later revisions can be *re-affirmed* as still fitting.

Verification notes: bibliographic data (authors, venue, pages, DOI) were checked against OpenAlex records, the ACM SIGMOD/DBLP mirror conference tables, or the paper's own front matter. Quotes come from full texts I could actually read: the Neptune SIGMOD '86 paper, the 1988 Intermedia paper, the PIE reports, Microcosm CSTR 92-15, the Aquanet HT'91 and ECHT'92 papers, Marshall and Shipman HT'93, the preprint of "Formality Considered Harmful", Halasz's 1991 keynote transcript, Grønbæk and Trigg 1994, Griffiths et al. 2002, Jacobson and Spiro 1993, and Whitehead's 2000 dissertation. Items I could only see as abstracts or search snippets are marked as such. The ACM DL, dblp.org and bitsavers refused automated fetches, so the full texts of Delisle and Schwartz 1987, CoVer, Take CoVer and Østerbye 1992 were **not** read. For those I rely on abstracts and on Whitehead's dissertation, which analyses each of them in detail.

Nothing here duplicates the prior survey: none of Intermedia, Microcosm, Neptune, PIE, CoVer, Dexter, NoteCards, Aquanet, VIKI or Shipman appears in [`labeled-viewpoints/notes/academic-research.md`](../../labeled-viewpoints/notes/academic-research.md), [`labeled-viewpoints/notes/federated-and-attributed-wikis.md`](../../labeled-viewpoints/notes/federated-and-attributed-wikis.md) or the other labeled-viewpoints files. ## Link sets stored separately from documents and swappable over the same documents (Intermedia webs, Microcosm linkbases, Chimera, OHP/FOHM, HyperDisco, HAM, TextNet, paths)

### Takeaway
From 1985 to 1995 the "separable link set" was the mainstream hypertext architecture. Intermedia's **webs** and Microcosm's **linkbases** both overlay a named, swappable set of anchors and links on documents the set does not own, which is an exact precedent for F1 and F2. Neither was used, as far as any source shows, to encode *rival interpretations* of a corpus. Webs served per-course or per-user contexts. Linkbases served "author's links plus my links". Selection was crude: one web open at a time, or linkbases toggled in a filter chain. Only Microcosm had anything like combination (a merge utility for linkbases, and "applications" that intersect or include one another). Comparison between link sets was never built. The later Southampton work (FOHM and Auld Linky) generalised the idea to *context objects attached to any part of a structure*, and it explicitly treated versions as one kind of context.

### Cited Findings

**Intermedia webs (Brown IRIS, 1985–1991)**
- Citation: N. Yankelovich, B. J. Haan, N. K. Meyrowitz, S. M. Drucker, "Intermedia: The Concept and the Construction of a Seamless Information Environment," *IEEE Computer*, January 1988 (21(1); the scanned copy's pages run from 81 to the mid-90s). — [PDF copy](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)
- Mechanism, verbatim: "In Intermedia, block and link information is not stored within individual documents but is superimposed on them. Webs maintain the block and link information, allowing one or more users to work within their own context undistracted by blocks and links created by others sharing the same computing resources." The paper contrasts this with systems where "links are global—all links are available at all times to all users." — [Yankelovich et al. 1988](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)
- Selection is one web at a time: "opening a web imposes a particular set of blocks and links on a set of documents while that web is open. Thus, webs allow different users to impose their own links on the same document set. Although only one context can be viewed at a time, users can easily switch contexts by closing one web and opening another. In the future, webs will also serve as the focus for keyword searching operations." — [Yankelovich et al. 1988](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)
- A web is a prerequisite for seeing any structure: "we must first define a context by opening an existing web or by creating a new one. If a web is not open, we can still open and edit the documents even though no link and block information will be visible." The worked example opens a web named "Bio 106". — [Yankelovich et al. 1988](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)
- Anchors are "blocks": sub-document selections that belong to the web, not to the document. Rights such as "Annotate" let a user "create links to or from the document but … not edit its content." — [Yankelovich et al. 1988](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)
- Corpora were organised as course webs, for example "Context 32: A Web of English Literature, designed by Brown University English professor George Landow," alongside biology materials. — [Yankelovich et al. 1988](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)
- A secondary source claims more: "Intermedia supports the concept of webs, composite entities that have many nodes and links between them. A link can belong to one or more webs." I did not verify the multi-web membership claim in a primary source. — [Balasubramanian 1994, state-of-the-art review](http://csis.pace.edu/~marchese/CS835/Lec3/balasubramanian94.pdf)
- Whitehead's containment data model of Intermedia places document, block, link and web as separate stored entities: the web contains links and blocks by reference, and documents live in the file system. — [Whitehead 2000 dissertation, Fig. 9](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
- Portability: Landow and Kahn ported the Intermedia "Dickens Web" to Storyspace and Interleaf WorldView and had 15 experienced users evaluate it. They concluded "hypertext documents can exist independently of specific hypertext systems," and reported on "multiple linking from a single point, and web views." — G. P. Landow and P. Kahn, "Where's the Hypertext? The Dickens Web as a System-Independent Hypertext," ECHT '92, pp. 149–160, [DOI 10.1145/168466.168515](https://doi.org/10.1145/168466.168515) (abstract via OpenAlex)

**Microcosm linkbases (Southampton, 1988–)**
- Citation: A. M. Fountain, W. Hall, I. Heath, H. C. Davis, "MICROCOSM: An Open Model for Hypermedia with Dynamic Linking," ECHT '90, Cambridge University Press, pp. 298–311. — [ECHT'90 table of contents (DBLP mirror)](http://www.sigmod.org/publications/dblp/db/conf/echt/echt90.html)
- Mechanism (from the 1992 extended report, H. Davis, W. Hall, I. Heath, G. Hill, R. Wilkins, CSTR 92-15, "MICROCOSM: An Open Hypermedia Environment for Information Integration"): "No mark-up is imposed on the information … Instead all information concerning links is stored in link databases or linkbases." Messages pass through "a chain of filters … Filters in Microcosm are independent processes, and may be dynamically installed, removed or reordered … Particularly important filters are the linkbases." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)
- Several link sets over the same documents: "it is possible to have more than one linkbase in place at any time. A common configuration for Microcosm is to have one linkbase that contains a set of links over a set of documents that was defined by the original author and for each user to have their own linkbase into which they store their own links and annotations. The idea may be extended to allow shared workspaces." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)
- Combining link sets: "We have produced a program which enables users to manipulate linkbases by such processes as merging links from other linkbases, deleting global references to files that have been removed and changing the scope of links." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)
- Part-level anchoring by content: specific links (a point in a particular document), local links ("a particular object at any point in a specific document") and generic links ("a particular object at any position in any document"). Local and generic links have "dynamic source anchors" that "allow a destination to be fixed just once." An empirical aside: "authors had made 70% of their source anchors on only one or two complete words." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)
- Named containers of documents plus linkbases: "we have defined a concept of an application which is the closure of all files and linkbases which comprise a particular system. **Applications may intersect with others or include others.**" Whitehead describes Melly's Microcosm versioning work as building on these "context-like structures called applications that contain references to an active set of documents and links." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html); [Whitehead 2000, §3.6](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
- The editing and versioning problem was stated but not solved. "Since links are separated from the nodes, there is a problem if documents are edited … anchors are recorded in terms of absolute position … the information in the linkbase will become outdated." And: "If documents have been edited, then are the links to the old version or the new version? Do we need to keep versions of the linkbase as well?" (See the next question for Microcosm's date-stamp workaround.) — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)

**HAM (Hypertext Abstract Machine, Tektronix)**
- B. Campbell and J. M. Goodman, "HAM: a general purpose hypertext abstract machine," *CACM* 31(7):856–861, 1988. From the abstract: "The storage system consists of a collection of contexts, nodes, links, and attributes that make up a hypertext graph. The versatility of the HAM can be illustrated by showing how Guide buttons, intermedia webs, and NoteCard FileBoxes can be implemented using its storage model." — [DOI 10.1145/48511.48515](https://doi.org/10.1145/48511.48515) (abstract via OpenAlex)
- A secondary summary gives the storage model as "graphs (networks of nodes and links containing one or more contexts), contexts (partitions of data within a graph), nodes, links, and attributes." — [Balasubramanian 1994](http://csis.pace.edu/~marchese/CS835/Lec3/balasubramanian94.pdf)

**Chimera (UC Irvine, software-engineering link server)**
- K. M. Anderson, R. N. Taylor, E. J. Whitehead Jr., "Chimera: Hypertext for Heterogeneous Software Environments," ECHT '94, pp. 94–107. From the abstract: "Anchors are established with respect to interactive views of objects, rather than the objects themselves. Composable, n-ary links can be established between anchors on different views of objects stored in distinct object bases." — [DOI 10.1145/192757.192783](https://doi.org/10.1145/192757.192783) (abstract via OpenAlex)
- Whitehead's summary: "A Chimera link is defined as a set of anchors, and anchors are defined on … views … A view is modeled as a (viewer, object) pair." Chimera "provides storage for anchors, links, and views, but does not … control, the linked objects." His versioning requirements for ChimeraVP include "It must be possible to version links" and "It must be possible to version structure." — [Whitehead 2000](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)

**OHP, FOHM and Auld Linky (the open-hypermedia generalisation)**
- The Open Hypermedia Protocol was a client-to-link-server protocol. Its rationale: "systems support hypertext functionality by storing links in link services; these links may then be superimposed on, or included into the document by the client browser. However, there is no standard protocol." The 1990s OHP draft I read has no notion of context. — [Davis, Millard, Reich, "OHP – Communicating between Hypermedia Aware Applications"](https://eprints.soton.ac.uk/250733/5/ohp2.htm)
- FOHM: D. Millard, L. Moreau, H. Davis, S. Reich, "FOHM: a fundamental open hypertext model for investigating interoperability between hypertext domains," Hypertext 2000, pp. 93–102. — [DOI 10.1145/336296.336334](https://doi.org/10.1145/336296.336334)
- Context in FOHM and Auld Linky, as described by J. Griffiths, D. E. Millard, H. Davis, D. T. Michaelides, M. J. Weal, "Reconciling Versioning and Context in Hypermedia Structure Servers" (Metainformatics Symposium MIS 2002, LNCS, pp. 118–131): "Queries can be sent with an associated context description, in this case Linky matches the pattern, but then culls away any parts of the structure whose context objects do not match that of the query. It then checks that the culled structure still matches the original pattern before returning it." A contextual server "allows for many different views on a given structure, depending on the viewer's position in n dimensional context space." — [mis02.pdf](https://eprints.soton.ac.uk/256829/1/mis02.pdf); [Springer](https://link.springer.com/chapter/10.1007/3-540-44872-1_13)
- The "concept" structure speaks to the homonym problem: "Associations of type 'concept' that relate several objects that represent the same conceptual entity. Context objects attached to the bindings of the Association implement conditional membership of the concept. Thus the same concept can be seen differently according to the context of the viewer." — [Griffiths et al. 2002](https://eprints.soton.ac.uk/256829/1/mis02.pdf)
- Auld Leaky: D. T. Michaelides, D. E. Millard, M. J. Weal, D. De Roure, "Auld Leaky: A Contextual Open Hypermedia Link Server," LNCS 2002, pp. 59–70. — [DOI 10.1007/3-540-45844-1_6](https://doi.org/10.1007/3-540-45844-1_6) (metadata via OpenAlex)

**HyperDisco**
- U. K. Wiil and J. J. Leggett, "The HyperDisco Approach to Open Hypermedia Systems," Hypertext '96, pp. 140–148. It is an object-oriented platform "supporting intertool linking, computation, concurrency control, notification control, version control, access control, query and search," with the aim of extending tools "to handle multiple collaborating users and multiple versions of shared artifacts." — [DOI 10.1145/234828.234842](https://doi.org/10.1145/234828.234842) (abstract via OpenAlex)
- Follow-on: "Workspaces: The HyperDisco Approach to Internet Distribution," Hypertext '97, pp. 13–23. — [DOI 10.1145/267437.267439](https://doi.org/10.1145/267437.267439). Whitehead's assessment is that its "version control component supports only state-based versioning." — [Whitehead 2000](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)

**Typed relationships between works (Trigg's TextNet taxonomy)**
- R. Trigg, *A Network-Based Approach to Text Handling for the Online Scientific Community*, PhD thesis, University of Maryland, November 1983 (TR-1346). The first half was published as Trigg and Weiser, "TEXTNET: A Network-Based Approach to Text Handling," *ACM TOIS* 4(1):1–23, 1986. — [Trigg's thesis page](http://www.workpractice.com/trigg/thesis-default.html)
- Bernstein's review of the link-type chapter lists "Normal links" and "Commentary links" including *Refutation, Support, AlternateView, Rewrite, Update, Correction, isSupersededBy, isRefutedBy, isSupportedBy*, and under Commentary "Argumentation: invalid, insufficient, … alternative, strawman." Bernstein adds that NoteCards users "tended not to assign types to links, lest they choose the wrong type," and that "many hypertext system designers abandoned typed links completely." — [Eastgate, "Link Types: a second look"](https://www.eastgate.com/HypertextNow/archives/Trigg.html)

**Overlay paths over material one does not own**
- Walden's Paths (Texas A&M, from 1995): "a mechanism for overlaying linear paths over World-Wide Web material. The path structure does not alter the pre-existing structure of the original material, but provides a means for organizing and contextualizing the collection." It was used "by teachers and students in eight high-school art and music classrooms." One lesson: "while teachers find paths easy to integrate in the classroom, they find it difficult to find time to author paths from scratch." — [Furuta, Shipman et al., "Ephemeral Paths on the WWW" (archived)](http://web.archive.org/web/2005/http://www.csdl.tamu.edu/~furuta/wpwww8/). The venue is not printed in the retrieved text; the URL suggests WWW8 (1999), which is unverified.
- NoteCards precedents: R. H. Trigg, "Guided tours and tabletops: tools for communicating in a hypertext environment," *ACM TOIS* 6(4):398–414, 1988 ([DOI](https://doi.org/10.1145/58566.59299)). Also P. Zellweger, "Scripted Documents: A Hypermedia Path Mechanism," Hypertext '89, pp. 1–14 ([HT'89 table of contents](http://www.sigmod.org/publications/dblp/db/conf/ht/ht89.html)).

**Set-based alternative to links**
- H. Van Dyke Parunak, "Don't Link Me In: Set Based Hypermedia for Taxonomic Reasoning," Hypertext '91, pp. 233–242. For taxonomic reasoning "an analyst viewing one node thinks not in terms of linking it to another node, but of including it in or excluding it from a set of related nodes." HyperSet supports "intersecting sets of nodes," and the paper argues for a hybrid "that can concurrently support both set and graph manipulations." — [DOI 10.1145/122974.122998](https://doi.org/10.1145/122974.122998) (abstract via OpenAlex)

### Inferences
- **Intermedia webs:** F1 yes, down to part level (blocks), and F2 yes (links live in the web). They lack F3 (no web-from-web derivation is described) and F4 (blocks carry no document revision). The one-web-at-a-time rule means they also lacked any side-by-side comparison of two webs, which is exactly the "comparing was too hard" failure the prior survey found.
- **Microcosm linkbases and applications:** F1 yes (documents in applications; generic and local links anchor on content rather than position), F2 yes (links live in linkbases), and F3 only weakly (applications "intersect … or include" each other, and a linkbase-merge utility existed). F4 is partial, via date stamps (next question). No source shows linkbases being used for rival interpretations; the documented use is author-versus-personal layers. So the "rival schools as rival link sets" use of this architecture is a precedent in potential only, not in practice.
- **FOHM/Auld Linky context objects** are the closest *formal* ancestor of an embedding. Context attaches to *any* node of a structure, including a single binding of a link. That makes it F1 and F2 at part level. Its "concept" association with context-conditional membership is a direct answer to "two people name the same article 'institution'". Griffiths et al.'s claim that "versioning is a specific kind of contextualisation" bears on F4. What it lacks is F3: contexts were attribute spaces such as age or expertise, not forkable named objects.
- **HAM** shows that "webs" and "contexts" were seen as the same storage primitive by 1988.
- **Chimera** and **HyperDisco** add nothing specific to multiple perspectives. Their relevance is that link structure needed versioning of its own, separate from the versioning of the works it connects.
- **TextNet's typed relations** (Refutation, AlternateView, isSupersededBy) anticipate F2's *content*, meaning typed inter-entity relations that encode disagreement, but not its *container*. The recorded reluctance to type links is a warning for any design that asks contributors to classify relationships up front.
- **Parunak's HyperSet** is the "tag" end of the spectrum: aggregate set membership. It is a useful foil for the user's point that an embedding differs from a tag by having composite structure.

### Gaps
- No primary source found that Intermedia webs, Microcosm linkbases or FOHM contexts were ever used to represent rival *interpretations* of one corpus. The documented uses are per-course, per-user and per-audience (age or expertise).
- Could not confirm from a primary source that an Intermedia link could belong to more than one web (secondary claim only).
- Did not obtain Meyrowitz's OOPSLA '86 Intermedia architecture paper or the 1990 Microcosm paper's full text. The Microcosm details above come from the 1992 extended report.
- No comparison tool for two link sets over the same documents was found in any of these systems.

## Partitioning a hypertext into contexts/layers that branch and merge (Neptune/HAM, PIE, CoVer, Østerbye/HyperPro, HyperProp, Dexter, Halasz, Whitehead) — and how link endpoints were pinned to versions

### Takeaway
F3 and F4 have their deepest precedents here. **PIE** (Goldstein and Bobrow, Xerox PARC, 1980) had named **contexts** built as stacks of **layers**, alternative contexts that PIE could diff, and merges recorded as a new layer with a description of "the contexts participating in the merger and the basis for the merger". It also had **perspectives** whose name spaces were kept independent because "one agent cannot know the names chosen by another". Halasz called PIE's versioning model the one hypertext should "adopt and improve on".

**Neptune/HAM contexts** (Delisle and Schwartz, 1986–87) gave collaborating authors private, branchable copies of a hypertext and merged them back. Neptune also offered the two link-pinning modes F4 needs: attach to "a particular version of a node" or to "the 'current' version", with a saved history of attachment offsets.

The 1992–2001 literature (CoVer, HyperPro, HyperProp, Whitehead) settled on **composites plus revision-selection rules** (latest, as-of-time, by-label) as the way to version link structure without duplicating links.

Practice evidence is thin. Halasz in 1991 found essentially no follow-up work, and the leading evaluation-grounded motivation (SEPIA → CoVer) concerned parallel work and alternatives in co-authoring, not rival interpretations.

### Cited Findings

**Halasz's agenda (framing for the whole thread)**
- F. G. Halasz, "Reflections on NoteCards: Seven Issues for the Next Generation of Hypermedia Systems," Hypertext '87, pp. 345–365, republished in *CACM* 31(7):836–852, July 1988. — [DOI 10.1145/48511.48514](https://doi.org/10.1145/48511.48514); [HT'87 table of contents](http://www.sigmod.org/publications/dblp/db/conf/ht/ht87.html)
- In the Hypertext '91 closing plenary transcript, Halasz restates the seven issues as search and query, composites, virtual structures, computation, versioning, collaborative work, and tailorability. — [Halasz, "Seven Issues: Revisited" (1991 transcript)](https://www.eastgate.com/hypertext/Halasz/Halasz7Rev.pdf)
  - On composites: "the basic hypermedia model lacked a composition mechanism, that is, a way of representing and dealing with groups of nodes and links as unique entities separate from their individual components … all aspects of the hypermedia should support inclusion, that is, part-of, relations as a construct distinct from the standard kind of reference links." — [Halasz 1991](https://www.eastgate.com/hypertext/Halasz/Halasz7Rev.pdf)
  - On virtual structures (subtitled "Dealing with Change"): "virtual structures are defined by specifying a description of their components that is reified by a search procedure whenever the structure is accessed or instantiated." — [Halasz 1991](https://www.eastgate.com/hypertext/Halasz/Halasz7Rev.pdf)
  - On versioning: "A good versioning system will allow users to maintain and manipulate a history of changes to their networks. It will also allow users to simultaneously explore several alternative configurations … The goal is to adopt and improve on the versioning mechanism that appeared in the PIE system … Brilliant versioning model." — [Halasz 1991](https://www.eastgate.com/hypertext/Halasz/Halasz7Rev.pdf)
  - His 1991 assessment of progress: "Basically, none. I could find no published work on versioning in hypermedia systems after Mayer Schwartz and Norm Delisle's Contexts work in the CSCW '86 conference … whether, in fact, versioning is important or not is still, I think, an open issue." — [Halasz 1991](https://www.eastgate.com/hypertext/Halasz/Halasz7Rev.pdf)

**PIE (Goldstein and Bobrow, Xerox PARC, 1980–81)**
- Citation: I. P. Goldstein and D. G. Bobrow, "Descriptions for a Programming Environment," AAAI-80 (Stanford, August 1980). It is reprinted in *An Experimental Description-Based Programming Environment: Four Reports*, Xerox PARC CSL-81-3, March 1981, which also contains "Representing Design Alternatives" and related reports; "A Layered Approach to Software Design" is CSL-80-5. — [CSL-81-3 scan](http://worrydream.com/refs/Goldstein%20-%20PIE%20four%20reports.pdf); [AAAI-80 record](https://mlanthology.org/aaai/1980/goldstein1980aaai-descriptions/)
- Perspectives: "Attributes of nodes are grouped into perspectives. Each perspective reflects a different view of the entity represented by the node." The attribute names of each perspective are local to it: "Originally, this was not the case … However, this conflicted with an important property that design environments should have, namely, that different agents can create perspectives independently. Since one agent cannot know the names chosen by another, we were led to make the name space of each perspective on a node independent." Perspectives "may provide partial views which are not necessarily independent … Attached procedures are used to maintain consistency between such perspectives." — [CSL-81-3](http://worrydream.com/refs/Goldstein%20-%20PIE%20four%20reports.pdf)
- Contexts: "All values of attributes of a perspective are relative to a context … When one retrieves the values of attributes of a node, one does so in a particular context, and only the values assigned in that context are visible. Therefore it is natural to create alternative contexts in which different values are stored for attributes in a number of nodes. The user can then examine these alternative designs, or compare them without leaving the design environment. Since there is an explicit model of the differences between contexts, PIE can highlight differences between designs. PIE also provides tools for the user to choose or create appropriate values for merging two designs." — [CSL-81-3](http://worrydream.com/refs/Goldstein%20-%20PIE%20four%20reports.pdf)
- Layers: "A context is structured as a sequence of layers … Retrieval from a context is done by looking up the value of an attribute, layer by layer." "Closing a layer is an operation that declares that the layer is complete. After contracts are checked, a closed layer is immutable. Subsequent changes must be made in new layers appended to the appropriate contexts." — [CSL-81-3](http://worrydream.com/refs/Goldstein%20-%20PIE%20four%20reports.pdf)
- Coordination and merge: "different designers place their contributions in separate layers. Thus, where an overlap occurred, the divergent values for some common attributes are in distinct layers. Merging two designs is accomplished by creating a new layer into which are placed the desired values for attributes as selected from two or more competing contexts … We do not, and indeed cannot, claim that PIE eliminates this complexity … Layers created by a merger have associated descriptions in the network specifying the contexts participating in the merger and the basis for the merger." — [CSL-81-3](http://worrydream.com/refs/Goldstein%20-%20PIE%20four%20reports.pdf)
- Whitehead calls PIE "the first change-oriented configuration management system". He notes that because it "only keeps changes in its composites … and since these changes can be arbitrarily composed to create new hypertexts, PIE differs from Neptune, HyperPro, and HyperProp." — [Whitehead 2000, §3.4.1](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)

**Neptune/HAM (Delisle and Schwartz, Tektronix)**
- N. Delisle and M. Schwartz, "Neptune: a Hypertext System for CAD Applications," ACM 1986. The front-matter stamp "0-89791-191-1/86/0500/0132" corresponds to SIGMOD '86, p. 132 onward; I inferred the venue from that stamp. — [paper scan](https://papers.cumincad.org/data/works/att/31d5.content.pdf)
  - "The HAM … maintains a complete version history of the hypergraph and provides rapid access to any version of a hypergraph." — [Neptune 1986](https://papers.cumincad.org/data/works/att/31d5.content.pdf)
  - **Link pinning (F4 precedent), verbatim:** "Each end of a link can be attached to an offset within the contents of a node … Additionally, Neptune supports two mechanisms for associating the link attachment with versions of a node, the link attachment may refer to a particular version of a node or it may always refer to the 'current' version of the node. The former mechanism is a useful primitive for building a configuration manager. The latter form of attachment is best thought of as an automatic update mechanism, a history of link attachment offsets is saved, allowing the link to be attached to different offsets for each version of the node." — [Neptune 1986](https://papers.cumincad.org/data/works/att/31d5.content.pdf)
  - On the state of the art: "Neptune and Xanadu provide the capability for complete version histories at the granularity of 'writes' from a text editor. Both systems allow side-by-side comparison of different versions of the same node. Most hypertext systems include a facility that ensures that a link attached to an old version retains an attachment in a corresponding place in a new version." — [Neptune 1986](https://papers.cumincad.org/data/works/att/31d5.content.pdf)
- N. M. Delisle and M. D. Schwartz, "Contexts—a partitioning concept for hypertext," *ACM Transactions on Office Information Systems* 5(2):168–186, 1987. A conference version, "Contexts, a Partitioning Concept for Hypertext," appeared at CSCW '86. The abstract says existing systems "provide poor support for collaboration among teams of authors … several models for forming partitions in a hypertext database are examined and contexts, a partitioning scheme that supports multiperson cooperative efforts, are introduced. - Whitehead's analysis of Neptune contexts:
  - "A composite (context) is just a container object … When each collaborator works within a separate copy of the composite, it provides the appearance that each collaborator is working on their own individual paper. The drawback … each individual's contributions must later be merged." — [Whitehead 2000, §3.4](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
  - "Composites collect together into one abstraction three concerns that are typically separated: collections … workspaces … and configurations," and they "address a uniquely hypertext problem, that of how to consistently version links between a consistent set of objects." — [Whitehead 2000, §3.4](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
  - "Due to the use of single containment, objects and links can only belong to a single context, and hence when a new context is created … all objects and links within the context are duplicated … Neptune uses more objects than any other system to represent the scenario … it has the advantage of eliminating the need for revision selection rules." - K. Østerbye, "Structural and Cognitive Problems in Providing Version Control for Hypertext," ECHT '92, pp. 33–42. — [DOI 10.1145/168466.168484](https://doi.org/10.1145/168466.168484); full text not read.

- HyperPro mechanics, per Whitehead: "HyperPro contains the entire versioned object (and hence all of its revisions) within contexts … The same versioned items, and their revisions, simply belong to multiple containers … one endpoint of its GenericVersionLink is a versioned object … This dilemma is solved by the revision selection rule associated with each context … the revision selection rule can be modified to pick a new revision without changing the link." — [Whitehead 2000, §6.3](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)

- F. G. Halasz and M. D. Schwartz, "The Dexter Hypertext Reference Model," *CACM* 37(2):30–39, February 1994. It came out of workshops held in 1988–89. — [DOI 10.1145/175235.175237](https://doi.org/10.1145/175235.175237)

**Whitehead's synthesis: how to version link structure and pin endpoints**
- E. J. Whitehead Jr., *An Analysis of the Hypertext Versioning Domain*, PhD dissertation, UC Irvine, 2000 ([PDF](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)). The condensed version is E. J. Whitehead, "Design spaces for link and structure versioning," Hypertext '01, pp. 195–204 ([DOI 10.1145/504216.504265](https://doi.org/10.1145/504216.504265), per search result).
- Links as independent objects: "the versioned object approach … permits the creation of composites containing a consistent set of documents and links, such as the most recent revision as of a specific time, or a specific snapshot … By-reference containment also allows the creation of containers that model a link structure by containing a single revision of multiple links, in this way capturing a link structure." — [Whitehead 2000, §8.5.1](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
- Revision selection rules versus link proliferation. Without rules, "the only way to satisfy the criteria [point at the latest revision, but preserve old endpoints] is by creating a new link." With them, "By using the versioned object as the link endpoint, and then letting the revision selection rule choose the specific revision, the need to duplicate link l … is eliminated. Including time in the revision selection rules allows prior link endpoints to be recovered … **Label-based revision selection has the additional benefit of creating internally consistent hypertext structures, assuming the hypertext was consistent when the labels were applied.**" — [Whitehead 2000, §8.5.2](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
- On the field: "existing hypertext versioning systems have only provided a single link versioning mechanism, without exploring design tradeoffs." — [Whitehead 2000](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)
- Lineage: "The CoVer, VerSE, and HyperPro systems, along with versioning support for the Nested Context Model in HyperProp, and Melly's versioning support for Microcosm all share Neptune's goal of exploring how to support hypertext structure versioning, and team document authoring, using composites." — [Whitehead 2000, §3.4](https://ics.uci.edu/~ejw/papers/whitehead_diss.pdf)

**Microcosm's pragmatic answer to F4 (date stamps plus warnings)**
- "All links contain a date stamp for the source and destination documents, which should match with the document's own date … Whenever a document is loaded all specific links from the document are checked. If any of these links have a date for the source document that is earlier than the date of the document itself, the user is warned. Whenever a link is followed to a document, the date of the destination document is checked against the date of the link. Again, if they do not match the user is warned." A link-aware editor "finds all references to the document in linkbases that are currently available, and updates these link anchors when editing is complete." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)
- The authors' own assessment: "This solution keeps the user aware of any inconsistencies, but makes no attempt to fix them." Guaranteed consistency "seems inherently fragile." The proposed future: "Versions of documents and link bases are maintained automatically, and on traversing a link to a document, the user is able to step back through previous versions of the document." — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)

**Walden's Paths Path Manager (F4 in a curatorial setting)**
- "Typically a collection's maintainer has to assess the relevance of changes with little system aid. This paper describes the Walden's Paths Path Manager, which assists a maintainer in discovering when relevant changes occur to linked resources." — [Francisco-Revilla, Shipman, Furuta, Karadkar, Arora, "Managing Change on the Web," 2001 (ERIC ED459818)](https://eric.ed.gov/?id=ED459818)

### Inferences
- **PIE** is the single closest precedent to the embedding idea as a whole:
  - F3: named contexts, alternatives, and diff and merge between contexts.
  - Merge provenance: "contexts participating in the merger and the basis for the merger".
  - Name spaces: per-agent perspectives with independent names, which is the user's "names are not synonyms" point.
  - F4, partially: closed, immutable layers.
  - What it lacks: prose and passages (F1 at part level). It was a programming environment, and I found no use for rival interpretations.
- **Neptune/HAM contexts** cover F1 (nodes and spans in a context), F2 (links in a context), F3 (child contexts with merge and derivation history) and F4 (per-link choice between "particular version" and "current version with offset history"). The single-containment design duplicated everything on fork. That suggests an embedding should hold **references with a revision selector** (the HyperPro/CoVer/HyperProp route), not copies.
- **The F4 design space already has names:**
  - pin to a specific revision (Neptune "particular version"; Whitehead "specific revision explicitly selected");
  - float to current (Neptune "current" with saved offsets; revision selection rule "latest");
  - pin by label or baseline (Whitehead's label-based selection).

  The user's "re-affirm a later revision as still fitting" is, in these terms, **moving a label forward after a human judgement**. Microcosm's date-stamp warnings and the Walden's Paths Path Manager are the only precedents found that surface "this changed since you linked it" to a human. Neither records the human's verdict as a first-class, attributable act.
- **HyperPro's duplicated links lost their shared identity.** A relationship assigned to an embedding should keep a stable identity across revisions and forks, or cross-embedding comparison ("both schools draw this link") becomes impossible.
- **Cognitive overhead** is the recurring practical warning: naming new versions, choosing versions, deciding when an edit is a new revision (Østerbye; CoVer's automatic per-task versioning as the fix). Embedding membership and re-affirmation should default sensibly (for example, auto-record the revision at assignment and queue re-affirmation lazily) rather than ask on every edit.
- **Comparison support existed but was thin:** PIE's difference highlighting, CoVer's three merge tools, and Neptune/Xanadu side-by-side views of *node* versions. None compared two contexts' *interpretive* content. This is consistent with the prior survey's finding that comparing is the hard part.

### Gaps
- Full texts of Delisle and Schwartz 1987 (merge and conflict semantics of contexts), CoVer 1992, Take CoVer 1993 and Østerbye 1992 were not accessible to me; the characterisations above rest on abstracts, search summaries and Whitehead's analysis.
- No evaluation data found on *use* of contexts or layers by real teams beyond Take CoVer's SEPIA-motivated summary. Halasz in 1991 reported essentially no published versioning work since 1986.
- I did not verify the NCM "perspective" definition verbatim; it comes from a search summary of the Springer abstract.
- Whitehead's 2001 Hypertext paper was not read; the dissertation, which it condenses, was.

## Structure grown after the fact (Aquanet, VIKI/VKB, incremental formalization, "Formality considered harmful")

### Takeaway
The PARC and Colorado line of work found the same thing repeatedly: people do **not** commit to explicit structure early, and ask them to and they route around it.

- In Aquanet, a two-year analysis produced almost 2,000 nodes and more than 20 types, yet relations "were less commonly used than the tool's design anticipated". Users expressed relationships through **spatial layout**, and activity regions **emerged** and were reused in a later collaboration.
- The follow-ups built for this:
  - VIKI's spatial parser, which recognised implicit lists, stacks and composites heuristically, with the user confirming;
  - HOS's system-suggested "incremental formalization";
  - the general diagnosis that users fear "prematurely committing to a specific perspective" and "cannot agree with anyone else on what the formalization should be".

This supports the user's intuition that schools "pull together" later. It also supplies mechanisms for recognising that pull-together.

### Inferences
- **Aquanet** covers F1 (virtual copies put the same object in several spatial contexts) and F2 (typed n-ary relations), plus schema-by-reference composition, a weak F3 for the *schema*. It lacks F4. The practice lesson is that explicit F2 relations were underused, and structure lived in layout and regions until late.
- **VIKI/VKB** cover F1 (collections and composites; an object in a collection) and implicit F2. VKB's navigable history is a form of F4 for the workspace, not per assignment. They lack F3.
- **HOS** is a pattern for *growing* F2 and typing after the fact: informal first, system-suggested formalization later.
- **For embeddings:**
  1. Allow membership to be assigned loosely, even provisionally, before any schema or coordinate system exists. This matches the user's "scattered across several articles, pulling together later".
  2. Give the system a role in *suggesting* that scattered divergences cohere. This would be the analogue of the spatial parser and HOS suggestions, for example clustering passages that co-occur in the same forks or cite each other, surfaced for human confirmation.
  3. Expect typed inter-entity relations to be underused unless they are cheap and optional.

  The Aquanet and Marshall–Shipman caution about collaborative intelligibility applies directly. Implicit, layout-like interpretive structure is hard for *other* people to read, which is precisely what comparing rival schools requires.
- **"Situational structure"** is Shipman and Marshall's name for a structure built for one task failing in the next. It is the practitioner's version of the user's point that coordinate systems are local and need translation between them.

### Gaps
- The VKB findings are from a search summary; the INTERACT 2001 paper was not read.
- The "Formality Considered Harmful" quotes are from the preprint; the 1999 journal wording was not checked line by line.
- Shipman and McCall's CHI '94 paper was read as an abstract only. I did not find how HOS decides *what* to suggest in detail, or its false-positive rates.
- Beyond the Hypertext '93 claims, I found no evaluation of how accurately spatial parsers recognise structure.

## Xanadu-era comparison: transclusion and versioned links (only what is new relative to the existing survey)

### Takeaway
Little new was found. The one addition is contemporaneous testimony that Xanadu and Neptune both kept complete version histories at edit granularity and supported side-by-side comparison of *node versions*, and that link survival across edits was then a baseline expectation. The existing survey's transpointing-window material already covers the comparison surface.

### Cited Findings
- "Neptune and Xanadu provide the capability for complete version histories at the granularity of 'writes' from a text editor. Both systems allow side-by-side comparison of different versions of the same node. Most hypertext systems include a facility that ensures that a link attached to an old version retains an attachment in a corresponding place in a new version." — [Delisle and Schwartz, Neptune 1986](https://papers.cumincad.org/data/works/att/31d5.content.pdf)
- A 1994 survey characterises Xanadu as "a write-once system … As links are created by users, the original document remains the same except for the fact that a newer version is created which would have references to the original version(s)." — [Balasubramanian 1994](http://csis.pace.edu/~marchese/CS835/Lec3/balasubramanian94.pdf)

### Inferences
- Xanadu's approach (immutable content addresses, with links that survive editing) is an F4 mechanism of the "pin and track" kind. The existing survey already notes this as the transclusion-based anchoring strategy. Nothing found here changes that.

### Gaps
- Did not pursue Xanadu link mechanics further, per the brief. Nothing new surfaced incidentally about Xanadu *link sets* as nameable or forkable collections.

## Hypertext work explicitly about multiple interpretations / perspectives / schools over one corpus

### Takeaway
The explicit "many interpretations of one corpus" line within the hypertext community came mostly from **scholarly and educational hypertext**, not from systems research.

- Landow's Intermedia course webs.
- Jones and Spiro's ECHT '92 paper tying hypertext to Skinner- and Rorty-style contextualist intellectual history. It holds that a text has "as many meanings as there are contexts within which the text might be placed, and the contexts themselves … reflecting the special interests and purposes of the interpreter."
- Cognitive Flexibility Theory's "thematic criss-crossing": the same case segments are revisited under several named thematic perspectives. This measurably improved transfer but not recall.
- Aquanet's stated aim to "help people form multiple interpretations of complex domains".

None of these provided forkable, versioned perspective containers. The systems research that had those mechanisms (PIE, Neptune, CoVer) aimed them at design alternatives and co-authoring, not at rival schools.

### Cited Findings
- R. A. Jones and R. J. Spiro, "Imagined Conversations: The Relevance of Hypertext, Pragmatism, and Cognitive Flexibility Theory to the Interpretation of 'Classic Texts' in Intellectual History," ECHT '92, pp. 141–148. — [DOI 10.1145/168466.168512](https://doi.org/10.1145/168466.168512) (full text not read); [ECHT'92 table of contents](http://www.sigmod.org/publications/dblp/db/conf/echt/echt92.html)
- The same authors' journal statement: "pragmatists like Quentin Skinner and Richard Rorty have encouraged us to view the text as having as many meanings as there are contexts within which the text might be placed, and the contexts themselves as reflecting the special interests and purposes of the interpreter … the emergence of more powerful hypertext systems has led writers like George Landow and Jay Bolter to suggest a convergence between this technology and our understanding of the problems of interpretation." — R. A. Jones and R. J. Spiro, "Contextualization, Cognitive Flexibility, and Hypertext: The Convergence of Interpretive Theory, Cognitive Psychology, and Advanced Information Technologies," *The Sociological Review* 42(1_suppl):146–157, 1994, [DOI 10.1111/j.1467-954X.1994.tb03414.x](https://doi.org/10.1111/j.1467-954X.1994.tb03414.x) (abstract via OpenAlex)
- **Cognitive Flexibility Theory hypertext, mechanism and evaluation:** M. J. Jacobson and R. J. Spiro, "Hypertext Learning Environments, Cognitive Flexibility, and the Transfer of Complex Knowledge: An Empirical Investigation," Center for the Study of Reading Technical Report 573, University of Illinois, April 1993. — [ERIC ED355508](https://files.eric.ed.gov/fulltext/ED355508.pdf)
  - Material: six cases subdivided into "minicases", each analysed under six "partially overlapping thematic dimensions of analysis" (for example Socially Constructed Nature of Technology; Actor Networks; Freedom–Control), with per-minicase "theme vectors" and "thematic commentaries that described how the conceptual themes are tailored to the particular case."
  - Technique: "the 'criss-crossings' of the minicases from the contrasting intellectual perspectives represented by the theme combinations were intended to demonstrate abstract conceptual interconnections across different case examples."
  - Design: 34 students, 17 per group.
  - Result: "although the control treatment led to higher performance on the measures of 'memory' for factual knowledge, the more hypertext-like treatment promoted superior knowledge 'transfer.'" The criss-crossing group also spent longer studying (M = 125 versus 83 minutes).
- **Landow's course webs** were the canonical literary use of Intermedia webs. See "Context 32: A Web of English Literature" ([Yankelovich et al. 1988](http://csis.pace.edu/~marchese/CS835/Lec4/r1081.pdf)) and the Dickens Web portability study ([Landow and Kahn 1992](https://doi.org/10.1145/168466.168515)).
- **Aquanet's aim** was framed in these terms: "we are interested in how the tool can be used to organize information to help people form multiple interpretations of complex domains." — [Marshall and Rogers 1992](http://web.archive.org/web/2005/http://www.csdl.tamu.edu/~shipman/viki/papers/echt92/echt92.html)
- **Microcosm's author-plus-personal linkbase layering** is documented as the "common configuration", which is interpretive layering at the level of the individual reader. — [CSTR 92-15](https://eprints.soton.ac.uk/250713/3/index.html)
- **FOHM's context-conditional "concept"** lets "the same concept … be seen differently according to the context of the viewer," for example a biography that is a single text in one context and a composite document in another. — [Griffiths et al. 2002](https://eprints.soton.ac.uk/256829/1/mis02.pdf)
- **PIE's perspectives** are one entity with several independently named views by different agents, kept consistent where interdependent by attached procedures. — [CSL-81-3](http://worrydream.com/refs/Goldstein%20-%20PIE%20four%20reports.pdf)

### Inferences
- **CFT's minicase × theme matrix** is the nearest *evaluated* analogue of "the same passages assigned to several named frames": each minicase belongs to several themes, each with a per-case commentary. It anticipates F1 at passage level and gives each assignment a commentary. It lacks F3 and F4; its themes were fixed by the designers. Its finding (better transfer, worse fact recall, more time) is the only experimental evidence found that reading one corpus through multiple named lenses changes what readers can *do* with it.
- **Jones and Spiro's contextualist framing** explicitly calls for an interpreter-relative container of contexts, which is the user's "embedding" in intellectual-history terms. I found no system they built that versioned or forked those contexts.
